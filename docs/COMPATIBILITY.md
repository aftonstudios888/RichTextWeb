# Compatibility and implementation boundaries

RichTextWeb 0.2 is an independent implementation of a portable flow model, rich editing engine, reusable browser controls, format converters and desktop hosts. This table describes implemented behavior and remaining boundaries. It is not a percentage estimate of Word/WPF parity or a claim to reproduce Microsoft's proprietary engine.

| Area                  | Implemented                                                                                                                                                                                                                    | Remaining boundaries                                                                                                                                                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Flow model            | FlowDocument, Section, paragraphs/runs/spans, typography, links, lists, tables/cells/columns, images, portable UI containers, owned collections, IDs and notifications                                                         | Full native System.Windows.Documents overload/interface coverage; arbitrary native UI children; full WPF property precedence, dispatcher, routed events, templates and animation                                                                          |
| Text positions        | Live UTF-16 text positions, insertion gravity, explicit snapshots, grapheme navigation, WPF-rule structural symbol indexing, context/text traversal and conversion APIs                                                        | Existing Offset/editing APIs remain UTF-16 for compatibility; synthetic paragraph separators and portable objects differ from WPF internal text containers; not binary/API drop-in parity                                                                 |
| Editing/history       | Structured rich edits, selection, transactions, search/replace, annotations, rectangular table edits, reversible structural/text patches, compact retained text deltas, unchanged live node identity through undo/redo         | Canonical-tree editing and diff discovery still traverse document-size data; no persistent rope or large-document virtualization; merged-cell row/column edits reject unsupported geometry                                                                |
| Review                | Authored tracked insertions/deletions, rich deleted fragments, accept/reject, reverse-order reject-all, comments/bookmarks, history and DOCX interop                                                                           | Full tracked formatting/moves/table-structure revisions, Word author-identity services and exhaustive revision nesting conformance                                                                                                                        |
| Collaboration         | Transport-neutral replicated character sequence, causal queues, deterministic concurrent text edits, per-character formatting, duplicate/tamper checks, version vectors, snapshots and engine bindings; local two-peer sample  | Network/authentication/persistence service is application-owned; full rich-structure/table/object coauthoring and production-scale tombstone compaction are outside the text protocol                                                                     |
| Browser rendering     | Keyed DOM reconciliation preserves unchanged nodes; browser text shaping/bidi; accessible editable surface; measured finite-page viewer, page ranges/navigation, break/keep/widow/orphan CSS behavior and overflow diagnostics | Detached layout/index traversal still scales with document size; no exact Word glyph/layout engine, full floating anchors, frames, drawing/equation editor, native line grid or GPU renderer                                                              |
| Layout/features       | Page setup/columns, first/even/default headers/footers, note metadata and page-linked footnotes, cached fields, TOC generation, page references and mail merge; advanced DOCX stories/sections                                 | Viewer uses browser column fragmentation; footnotes use a reserved area and report overflow rather than a recursive Word footnote solver; complex section pagination, automatic field dependency graphs and Word-identical print layout remain incomplete |
| Reusable controls     | RichTextBox/readers/page viewer, RichTextToolbar with formatting/insertion/layout/review dialogs, DocumentFeatures operations through shared engine, PDFEditorControl                                                          | Framework-native theming and physical assistive-technology/device qualification need platform-specific coverage                                                                                                                                           |
| DOCX/interchange      | JSON/text, sanitized HTML, Markdown, inert XAML, RTF subset; native DOCX headers/footers/notes/fields/TOC/bookmarks/comments/revisions; safe opaque drawing/math dependencies retained                                         | Office conversion remains bounded; retained drawings/math are opaque placeholders, not editable drawing/equation models; macros, OLE and active attachments are excluded; no universal lossless round-trip claim                                          |
| PDF                   | Selectable-text flow export; PDF.js visual preview/search/text extraction; editable reconstructed flow document and new PDF export; page/overlay manipulation and undo in reusable control                                     | Reconstruction uses geometric reading-order heuristics, can lose original structure/assets/layout, and is not arbitrary editing of original PDF text operators; no OCR, secure redaction, tagged-PDF/PDF-UA or PDF/A certification                        |
| Framework integration | Standard custom elements, typed React 18/19 adapter/hooks, .NET-style MVVM bindings, validated JSON bridge and C# client                                                                                                       | Vue/Angular use standard custom-element integration; these are not complete replicas of each framework's native control API                                                                                                                               |
| Native qualification  | Buildable shared C#, WPF/WebView2, WinUI and official Avalonia adapter projects; executable C#/Node protocol checks; Windows WPF smoke workflow and package artifacts                                                          | JavaScript still renders inside the WebView; WinUI/Avalonia runtime/device qualification is distinct from compilation; official Avalonia NativeWebView requires its provider's runtime license                                                            |
| Distribution          | ESM/CJS/types/maps, standalone editor and optional PDF bundle/assets, package-consumer tests, native package artifacts, CI-gated releases, npm provenance/checksums and GitHub Pages sample                                    | Package mechanics and automated checks do not establish full production or Microsoft-engine conformance                                                                                                                                                   |

## Migration approach

Keep FlowDocument at the application boundary. Use explicit symbol/text conversion when porting WPF position calculations; do not silently reinterpret UTF-16 offsets as structural symbols. Use the same editor engine for toolbar commands, document features, React/MVVM views and native bridge calls. Canonical JSON retains all RichTextWeb metadata; format-specific guarantees are documented in [FORMATS.md](FORMATS.md) and [PDF.md](PDF.md).

`FlowDocumentPageViewer` measures the browser's actual finite-height column layout and reports page ranges and overflows. Editable `RichTextBox` page mode remains a growing paper surface. Browser print, the page viewer and direct PDF generation are distinct layout paths and can wrap differently. Test the chosen path against representative documents and fonts.

The compatibility references are Microsoft's public [Flow Document overview](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/flow-document-overview), [RichTextBox overview](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/controls/richtextbox), and [TextPointer API](https://learn.microsoft.com/en-us/dotnet/api/system.windows.documents.textpointer). The implementation and original tests establish the claims above; an exhaustive Word/WPF conformance suite has not been completed.
